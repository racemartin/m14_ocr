# Development notes

This file is the project's committed home for build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- `JsonlDatasetRepository` (`src/chsa_triage/infrastructure/adapters/jsonl_dataset_repository.py`) rereads and rewrites the ENTIRE JSONL file on every `sauvegarder()`/`sauvegarder_plusieurs()` call (both dedupe by `identifiant`, dict-keyed). Never call `sauvegarder()` inside a per-item loop over more than a few hundred items; it's O(n²) and infeasible on real corpus sizes (confirmed on the real dataset). Always accumulate into a list and call `sauvegarder_plusieurs()` once. For an append-only audit file where entries may legitimately share an `identifiant` (e.g. `doublons_supprimes.jsonl`), use the module-level `ajouter_exemples_jsonl()` in the same file instead: it appends without the id-merge dedup.
- `LecteurCorpusFichierLocal` loads the whole source file into a pandas DataFrame at once unless constructed with `taille_bloc=N` (chunked pandas read, CSV/JSONL only). Real files here can be ~1GB (`ultramedical_preference.jsonl`, 966MB/109k records) on a ~5.8GB-RAM box; pass `--taille-bloc` (both `profiler_corpus.py --bloque` and `construire_dataset_pivot.py --taille-bloc`) for any source that large, or expect an OOM kill.
- **Pivot/anonymized-file split (since 08/09/2026)**: `data/processed/dataset_pivot.jsonl` (the original pivot) is NEVER mutated by `anonymiser_dataset.py`; it's read-only from that point on. Anonymized output goes to a SEPARATE file (`--sortie`, default `dataset_pivot_anonymise.jsonl`). "Already anonymized" is determined by `identifiant` presence in that output file (`RepositoryLectureEcriture.identifiants_existants()`), not by the `anonymise` field on the source pivot (which stays `False` forever on the source). `decouper_splits.py`/`verifier_repartition_splits.py` must point `--dataset` at the ANONYMIZED file, not the original pivot. This design exists so the original text is never lost, enabling `controler_qualite_anonymisation.py` to diff original-vs-anonymized on demand (including retroactively on old waves).
- `ExemplePivot.identifiant` is DETERMINISTIC (sha256 of `espace_noms:cle_naturelle`, see `nouvel_identifiant`), not random: regenerating the pivot from the same `data/raw/` files always produces the same ids. `espace_noms` must be finer than the pivot's `source` field when raw files share a natural-key space: confirmed on real data that `mediqal_oeq.jsonl` and `mediqal_mcqu.jsonl` share 1492 identical raw `id` values for genuinely different records (mcqu vs mcqm distinguished via the raw `task` field). `ConstruireDatasetPivotUseCase` treats two raw records that hash to the same `identifiant` as true exact duplicates and drops all but the first, archiving the dropped ones (never silently) to `data/processed/doublons_supprimes.jsonl` via `ajouter_exemples_jsonl`. Real counts found this way: FrenchMedMCQA 1/595, MedQuAD 48/16407, UltraMedical-Preference 12272/109353; see `docs/02_etape1_donnees/00_couverture_exigences_officielles.md` for the per-source natural-key design and the dedup investigation.
- Real Presidio/spaCy anonymization throughput measured on the real dataset: ~130-550ms per text field depending on length/language, dominated by spaCy NLP inference, not I/O. Full-dataset anonymization is estimated at ~19h wall time with the current per-field `AnalyzerEngine.analyze` calls (no batching). `anonymiser_dataset.py --limite N` (default 5000) makes this incremental/resumable via the pivot/anonymized-file split above. See `docs/02_etape1_donnees/00_couverture_exigences_officielles.md` for the measured breakdown and wave history.
- `SpacyVerificateurEntitesNommees.verifier()` (`src/chsa_triage/infrastructure/adapters/spacy_verificateur_entites.py`) caches the parsed spaCy `Doc` keyed by `(texte, langue)` in a small LRU (8 entries): `uc_03_02_controler_qualite_anonymisation.py` calls `verifier()` once per candidate found in a field, passing the same full text each time (measured up to 17 calls for one UltraMedical-Preference field), so without the cache the same text gets reparsed by spaCy repeatedly. Microbenchmark on a realistic text (17 repeat calls): ~0.12s cached vs ~1.24s uncached.
- `data/raw/`, `data/processed/`, `data/splits/` are gitignored: a fresh worktree/clone has none of the 6 source files. Regenerate them with the `telecharger_corpus.py` commands in the README before running any later pipeline step; no network access means the pipeline literally cannot be exercised end-to-end.
- `tests/infrastructure/test_presidio_anonymiseur.py` and `test_spacy_verificateur_entites.py` each instantiate a fresh `PresidioAnonymiseur`/spaCy pipeline per test, reloading `fr_core_news_md` + `en_core_web_sm` every time; the full `uv run pytest tests/ -v` suite takes ~15+ minutes wall time on this box, almost entirely NLP model load, not test logic. Prefer running a single test file/function while iterating; only run the full suite before considering work done.
- Verified empirically (not assumed) on real/realistic clinical sentences: `en_core_web_sm` tags age expressions (`"7-year-old"`, `"70 year old"`, `"45 years old"`, `"aged 3 years"`) as `DATE_TIME`, but `fr_core_news_md` currently does NOT tag equivalent French constructions (`"âgé (60 ans)"`, `"enfant de 2 ans"`, `"Age > 60 ans"`) the same way: the age-over-masking bug is real but currently EN-only with these model versions. `PresidioAnonymiseur._normaliser_ages` still normalizes both languages defensively. Full investigation and the NIR-recognizer/DATE_TIME-operator design it motivated: `docs/02_etape1_donnees/01_rapport_rgpd.md` §7.
- **Persisted human review of PII-residual candidates (since 09/09/2026, NF2)**: `controler_qualite_anonymisation.py`'s sampling is now INCREMENTAL: `--registre-echantillons` (default `data/processed/controle_qualite_identifiants_echantillonnes.jsonl`, `JsonlRegistreEchantillonsControleQualite`) excludes identifiants already sampled in a prior run, on both strata (`STRATUM_PRINCIPAL`/`STRATUM_SANS_ENTITE`), same pattern as `AnonymiserDatasetUseCase`/`--limite`. A candidate's stable key across runs is `CleCandidatRevision(source_liste, identifiant, champ, type_motif, debut, fin)` (`domain/model/decision_revision_humaine.py`); `source_liste` disambiguates the 3 candidate lists (`candidats_pii`/`candidats_faux_positifs`/`candidats_pii_sans_entite`) since the same `CandidatPiiResiduelle` dataclass backs two of them. Human decisions (`accepte`/`rejete`) persist in `data/processed/decisions_revision_humaine.jsonl` (`JsonlDecisionsRevisionHumaine`, upsert-by-key like `JsonlDatasetRepository.sauvegarder`, not append-only, since `--modify` corrects mistakes). `interfaces/cli/reviser_pii_residuelle.py verify` replays the comparison over the FULL cumulative sampled set (not just the latest QC report, which only covers that run's fresh batch) to surface every still-pending `VERDICT_REVISION_HUMAINE` candidate; this is why `ControleQualiteAnonymisation.max_faux_positifs_par_source` accepts `None` (unlimited) now, vs. the default cap of 10 used for the human-readable Markdown report. See `docs/02_etape1_donnees/01_rapport_rgpd.md` §7.5 for the full design rationale.
- **`decouper_splits.py --n` is a cumulative TARGET size, not a fresh-sample size, since 10/09/2026**: `DecouperSplitsUseCase` never reassigns the `split` of an `ExemplePivot` that already has one from a prior run; only examples with `split is None` are candidates. `--n N` pulls `N - (already assigned)` new examples (stratified sample among the unsplit candidates); omitting `--n` completes all remaining unsplit examples rather than recomputing everything. This replaces an earlier design where every run reshuffled ALL considered examples, which could silently move an example from `train` to `test` (or back) across runs: a train/test leak. `decouper_splits.py --dataset ... --n 5000` then later `--n 10000` on the same file leaves the first 5000 assignments untouched; `nombre_deja_assignes`/`nombre_nouveaux` on the use case distinguish prior-run vs this-run counts, and the returned dict is the cumulative total, not just this run's additions. `verifier_repartition_splits.py` needed no change; it just reads whatever splits currently exist. See `docs/02_etape1_donnees/00_couverture_exigences_officielles.md` ("Croissance stable...") for the full rationale and the two-alternatives comparison, and the module docstring of `uc_04_00_decouper_splits.py` for the algorithm.
- **Publication exclusion of PII-residual candidates, two-step (since 11/09/2026)**: before publishing the SFT subset, `reviser_pii_residuelle.py exporter` (a third, non-interactive CLI mode alongside `verify`/`modify`) writes `data/processed/identifiants_a_exclure_publication.jsonl` (`--sortie`), one `{identifiant, razon}` line per identifiant with at least one `VERDICT_CONFIRME` candidate (razon `confirme`) or one `VERDICT_REVISION_HUMAINE` candidate without a persisted `DECISION_ACCEPTE` (razon `pendant_revision_humaine`; `confirme` wins when an identifiant has both). Reuses the same replay engine as `verify` (`ReviserPiiResiduelleUseCase._rejouer_controle`, generalized `candidats_a_revoir(controle, verdicts=...)`), extended to also surface `VERDICT_CONFIRME`, which `verify`/`candidats_en_attente()` never did (those candidates are unambiguous regex hits and never go through human decision). `interfaces/cli/extraire_sous_ensemble_sft.py --dataset --exclusions --taille --sortie` then filters the anonymized pivot on `split is not None` minus that exclusion file (`ExtraireSousEnsembleSftUseCase`, `uc_04_02`); it is a filter/subtraction, never a re-sampler in the sense of never drawing NEW examples to make up a shortfall: if the result is short of `--taille` it reports the shortfall and tells you to widen `decouper_splits.py --n` first, rather than silently returning fewer examples. See README §9 for the full two-command flow.
- **`extraire_sous_ensemble_sft.py` truncates a surplus to exactly `--taille` (fixed 11/09/2026)**: an earlier version only ever subtracted and never trimmed, so a filtered result larger than `--taille` (e.g. 9926 available for a requested 5000) was written in full, silently publishing more than asked. `ExtraireSousEnsembleSftUseCase.executer()` now applies `echantillon_stratifie` (`application/echantillonnage.py`, the same plus-grand-reste algorithm used by `AnonymiserDatasetUseCase`/`DecouperSplitsUseCase`) when the post-exclusion result exceeds `taille_cible`, so the written count is exactly `taille_cible` whenever enough examples are available; `nombre_disponible_final` still reports the pre-truncation pool size (used by `manque`), while the new `nombre_tronque` reports how many were cut. `echantillon_stratifie` does not stratify by `split`, only by `(type_exemple, source)`; confirmed empirically (not assumed) in `tests/application/test_extraire_sous_ensemble_sft.py` that a random sub-sample of an already-~80/10/10 stratum stays within a few points of 80/10/10 without a second nested stratification layer. The CLI prints a per-strate `Strate | Total | train (%) | val (%) | test (%)` table of the WRITTEN result (`calculer_repartition_par_strate`/`formater_tableau_repartition`, uc_04_02), same presentation as `verifier_repartition_splits.py` but computed in-memory rather than by rereading the repository.
- **`decouper_splits.py` excludes examples with confirmed or pending PII-residual candidates (since 10/09/2026, extended 11/09/2026)**: `DecouperSplitsUseCase` takes an optional `obtenir_identifiants_pii_en_attente: Callable[[], set[str]]` (default: no exclusion, name kept for historical reasons) applied only to unsplit candidates, never to already-assigned examples. It is wired to `ReviserPiiResiduelleUseCase.identifiants_a_exclure_publication_set()`, which reuses `identifiants_a_exclure_publication()` (both CONFIRME and pending-review reasons); an earlier version only wired the narrower `identifiants_en_attente()` (pending-review only), missing confirmed leaks. The CLI needs the same adapters as `reviser_pii_residuelle.py verify` (`--original`, `--registre-echantillons`, `--decisions`, `--jeton-masque`) to build this callable. Rationale: block-by-candidate review would stall the pipeline, so examples with at least one unresolved PII candidate stay out of train/val/test until a human decision exists or the text is fixed; see `docs/02_etape1_donnees/00_couverture_exigences_officielles.md`.
- Regenerating `docs/diagrams/**/*.puml` outputs: this box has no `plantuml` CLI and no matching-JDK PlantUML jar preinstalled (system Java is 17; the latest PlantUML jar needs Java 21 for its PDF path, throwing `UnsupportedClassVersionError`). Workaround that worked: download an older jar built for Java 17 (e.g. `plantuml-1.2024.8.jar` from GitHub releases) for `-tpng -tsvg` (run those two together, not combined with `-tpdf`; a PDF failure aborts the whole invocation before png/svg get written), then convert the generated `.svg` to `.pdf` with `cairosvg` (`uv pip install --python <venv> cairosvg`, needs system `libcairo2` which is present) since PlantUML's own PDF export needs Apache Batik+FOP transcoders not bundled in the jar. A floating `note as X ... end note` placed before `start` in an activity diagram fails to parse (silently produces an "error" image with exit code 0); attach the note to a step after `start` instead (e.g. `note right ... end note` right after the first `:Action;`). Graphviz (`dot`) is ALSO absent and `sudo apt-get install` has no password: package/class diagrams that need graph layout fail `-tpng`/`-tsvg` with `Cannot run program "/opt/local/bin/dot"`. Fix: add `!pragma layout smetana` right after `@startuml` (before the shared-style `!include`) to force PlantUML's pure-Java layout engine instead of shelling out to Graphviz; needed for paquets/classes diagrams, and also confirmed needed for deploiement diagrams (`node`/`cloud`/`database`/`component` also route through Graphviz layout; activite/sequence diagrams render fine without it); no extra install needed. (`apt-get download <paquet>` works without root if you ever do want the real Graphviz .deb, but its dependency chain (libgvc6, libgd3, libgts, liblab-gamut1, ...) makes `smetana` the faster path for diagrams this size.)

## Writing style

Never use `" -- "` (double hyphen) or the em dash `—` as a sentence separator in this project's docs, comments, docstrings, or diagrams; use normal punctuation instead (comma, colon, semicolon, parentheses, or split into two sentences).
